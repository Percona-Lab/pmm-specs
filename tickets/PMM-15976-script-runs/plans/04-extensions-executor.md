# Plan 04: The executor in PMM Extensions (task level)

> Execution: see [00](00-roadmap.md#how-to-execute-these-plans). This plan is expanded into a full-depth plan, reviewed in a pmm-specs PR, before it starts.

**Goal:** PMM Extensions runs its four seeded task kinds on PMM Client hosts through pmm-managed's `ScriptsService`, with a real `pmm_agent` backend beside the Nomad one, the same history, steps, logs, files and run results as today, and no setting, payload or stored row that only works under Nomad.

**Architecture:** A third executor, `PmmAgentExecutor(BaseExecutor)`, in a new package `app/tasks/execution/executors/pmm_agent/`. It calls `/v1/scripts` through PMM's nginx with PMM Extensions' existing PMM connection (`settings.PMM`), the service-account token, and the second token of [ADR-09](../adr/ADR-09-who-may-start-a-run.md). A task row keeps its own backend; `TASKS.DEFAULT_BACKEND`, a start-up setting, decides how the four seeded kinds are seeded and what a new task gets, and a task on the `nomad` backend runs only while that default is `nomad`. Every run is followed to its end by the executor that dispatched it. Under `pmm_agent` each seeded kind is a neutral definition plus one wrapper script kept in PMM Extensions; the wrapper, its shared shell functions, the script, the arguments file and the configuration file travel inline as text `files` ([ADR-08](../adr/ADR-08-script-content-inline.md)). PMM Extensions generates each run's id and stores it before it asks for the start, so a lost answer is recovered by asking for that id. Run output is copied into PMM Extensions' own log store, anonymized as today and split into the steps the UI shows, and one follower holding one waiting `ListRuns` call hears of every run's end. The Nomad executor is not changed beyond the stop fix (Task 1) and an optional `TASKS.NOMAD` (Task 2); `nomad` stays the code default.

**Tech Stack:** Python 3.11, FastAPI, SQLModel, Celery 5.6, aiohttp through `app/core/requests/remote_api.py`, Alembic (tasks track), pytest with `aioresponses` and an aiohttp stub server; bash for the wrappers.

**Spec:** [spec §8](../spec.md#8-pmm-extensions), [§6.2](../spec.md#62-what-a-run-is), [§6.7](../spec.md#67-the-api), [§6.8](../spec.md#68-the-host-list), [§9.1](../spec.md#91-who-can-start-a-run), [§10.1](../spec.md#101-nomad-capabilities-and-what-replaces-each), [§11](../spec.md#11-tests), [§13 O5](../spec.md#13-risks-and-open-questions); [ADR-07](../adr/ADR-07-run-as-user.md), [ADR-08](../adr/ADR-08-script-content-inline.md), [ADR-09](../adr/ADR-09-who-may-start-a-run.md), [ADR-11](../adr/ADR-11-one-execution-path.md), [ADR-10](../adr/ADR-10-api-shape.md), [ADR-03](../adr/ADR-03-at-most-once.md), [ADR-14](../adr/ADR-14-mixed-versions-and-nomad-removal.md). The UI's generated types in percona/pmm are regenerated after this plan's PR is merged (plan 05).
- **Names are the roadmap's shared contract** (00 § "PMM Extensions, plan 04"): backend value `pmm_agent` in `TaskBackendEnum`; settings `TASKS.PMM_AGENT` (its own model) and `TASKS.DEFAULT_BACKEND`; payload environment `PMM_EXTENSIONS_TASK_TARGET`, `PMM_EXTENSIONS_TASK_DIR`, `PMM_EXTENSIONS_TASK_CONFIG_FILE`; step names `prepare-env` and `run-script`; wrapper exit 78 for "cannot be launched". pmm-agent sets `PMM_RUN_ID`, `PMM_RUN_DIR` and `PMM_RUN_OUTPUT_DIR`. A change to any of them goes through 00 first.
- **Limits are the roadmap's** (00 § "Limits"): per request, `files` 1 MiB in total, `stdin` 1 MiB, `command` and `env` together 64 KiB; 2 MiB per file read; 30 s for a `wait`; `start_within` at most 24 h; `max_output_bytes` at most 100 MiB; PMM Extensions always sends it (Task 6), so pmm-managed's 16 MiB default never applies to it. `files` content and `stdin` are text, valid UTF-8; binary content is not carried. A file's mode sets owner bits only (0400 to 0700), default 0600; a file can be marked sensitive, and then neither its content nor its SHA-256 is stored on PMM Server. PMM Extensions checks all of these before it calls `StartRun` and refuses a task that breaks one, with a clear error; pmm-managed and pmm-agent check again.
- **Secrets never enter the environment, the command or the run record** ([spec §8.3](../spec.md#83-what-the-payloads-assume), [§6.6](../spec.md#66-records-and-retention)). `meta.config`, `meta.args` and `payload`, which are encrypted at rest in `taskhistory.execution_request` (`app/tasks/execution_request_secrets.py:17-24`) [V], travel only as `files` content; the `config` and `args` files are marked sensitive. `command` is stored by pmm-managed in clear, so it carries the interpreter or the command and nothing else.
- **Nothing in this plan removes Nomad code.** The Nomad executor, its client library, `NomadLifecycle`, the certificate-expiry beat and the 1 s finishing probe stay in the release that ships this plan ([spec §10.2](../spec.md#102-two-releases)); plan 07 removes them. They are active while `DEFAULT_BACKEND` is `nomad`, or while a run that Nomad dispatched is not final, and idle otherwise. `TASKS.NOMAD` becomes optional (Task 2).
- **At most once** ([ADR-03](../adr/ADR-03-at-most-once.md)). The executor generates the run's id, stores it in the history and commits before it calls `StartRun`. A `StartRun` with an id that exists returns that record and starts nothing. A start that gets no answer is sent again with the same id, a bounded number of times, and is never marked failed on the spot. Errors of the new executor are never auto-retried by Celery, on `execute_task_queue` (`app/tasks/celery.py:257-262`) or `execute_task_by_name` (`:282-287`) [V].
- **Tests come first** for every task. New tests live under `tests/app/tasks/execution/executors/pmm_agent/` (new) and follow the suite's patterns: async tests, `polyfactory` factories, no real network.

## Review Focus

- **A Nomad run in flight when the default moves to `pmm_agent`**, across an upgrade or a reseeding of the four kinds. Expected: it is synced, stopped and read by the Nomad executor to its end, and a new run of the same task goes to pmm-agent (Task 2).
- **A user script that itself exits 78.** Expected: FAILED with the `run-script` reason, not UNLAUNCHABLE; only an exit 78 before the `run-script` mark is UNLAUNCHABLE (Tasks 4 and 6).
- **Output dropped before the `run-script` mark was read.** Expected: the mark may be among what was dropped, so from the gap on the output is taken as `run-script`: it is anonymized, and an exit 78 after it is FAILED, not UNLAUNCHABLE (Task 7).
- **An e-mail address in `run-script` output, with an anonymize mask.** Expected: replaced in the store and in the live stream, kept in `prepare-env`, with the same withheld-line ceiling as Nomad (`NOMAD_STEP_ANONYMIZE`, `app/tasks/execution/executors/nomad/steps.py:91-99`) [V]. File reads honor `anonymize` (Tasks 7 and 8).
- **A credential in `meta.args` or `meta.config`.** Expected: only in a sensitive file; not in `command`, `env`, a log line, or the run record (Task 5).
- **A Nomad run that is stopped.** Expected: its output is kept, and its log-capture hold is released after the sync that stores it (Task 1).
- **The second token.** Expected: keyed with `EXTENSIONS_INTERNAL_TOKEN` under the shared label, the same in the bundle and outside it, and never logged (Task 3).
- **A `StartRun` whose answer is lost.** Expected: the same `StartRun` is sent again with the stored id and starts nothing twice; with no answer at all the history stays RUNNING, is followed if pmm-managed has the run, and reads FAILED "never started" only after two checks in a row find no record; no Celery retry fires (Tasks 2 and 6).
- **A stop that pmm-managed holds because the host is away.** Expected: the history stays RUNNING with a "stop requested" event, and reads `stopped`, or `succeeded` if the script ended first, once the record is final (Tasks 1 and 9).
- **Two follower ticks that overlap.** Expected: one holds the named lock and one `ListRuns` call; the other returns at once; no run is synced twice (Task 9).

One method per RPC of [spec §6.7](../spec.md#67-the-api): `start_run`, `get_run(run_id, wait)`, `list_runs(final_after, from_now, wait)`, `get_run_logs(run_id, offset, limit)`, `stop_run`, `list_run_files`, `read_run_file(run_id, name, offset, length)`, `list_hosts`. Request and response models are pydantic models that mirror plan 02 Task 1's JSON: `RunState` is a `StrEnum` of the shared contract's states; a run carries `dropped_bytes`; a host carries `user`, `contained`, `capacity` and `queue`; `ReadRunFile`'s `data` arrives base64-encoded in the gateway's JSON and the client decodes it; `ListRuns` always returns a cursor, opaque to PMM Extensions.
- **Certificate verification:** `PMMSettings` gains `ssl_cafile: RelativeFilePathField | None = None`, the type `BaseRemoteAPI.ssl_cafile` has (`remote_api.py:640`) [V]. With `verify_ssl` on and a CA file set, the connection accepts only a PMM Server certificate that chains to that CA and names the address PMM Extensions dials. Every other user of `settings.PMM` passes the new field too. Which certificate the bundle uses is [spec §13 O5](../spec.md#13-risks-and-open-questions).
- **The second token:** header `X-PMM-Scripts-Token`, value HMAC-SHA256, hex, keyed with the internal token the two sides already share, over the label `pmm-managed-scripts-token` (00 § "pmm-managed, plan 02"); grpc-gateway forwards the header (plan 02). In PMM Extensions that internal token is `settings.EXTENSIONS_INTERNAL_TOKEN` (`app/core/config.py:774`) [V]: the token pmm-managed presents when it calls PMM Extensions, which PMM Extensions compares in `app/api/deps.py:110-111` and returns from `get_internal_token` (`app/core/security.py:58-67`) [V]. It is configured, or derived from `SECRET_KEY`, and construction fails when neither gives a value (`derive_internal_token`, `app/core/config.py:842-875`) [V], so it is never empty here.
